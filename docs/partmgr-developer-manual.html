Overview

What partmgr is from the inside, the principles that shaped it, and a map of this manual.

What this manual covers

The user manual explains what partmgr does. This manual explains how: after reading it you should be able to find your way in every source file, build and test partmgr, and change the way it reads or writes tables without breaking a disk.

Design principles

  • The table code knows no firmware. Reading, changing and writing tables (ptable.c, ptedit.c, ptwrite.c) reach the disk only through a read and a write function (PtDev). The same code runs on a UEFI block device and, in the tests, on a disk image file, where sfdisk and parted check every table it writes.
  • Nothing is written until Write. Every change is made on a PtTable in memory; only pt_write, pt_restore and pt_wipe write to a disk (decision P7).
  • Protection at the lowest level. The disk partmgr was started from, and a write-protected one, get no write function at all: no mistake in the interface can write them.
  • Only the table — or a wipe. The blocks partmgr writes are the MBR, the extended boot records and the GPT headers and arrays. The only write inside a partition is a wipe, of exactly that partition's blocks.
  • Damage is shown, not hidden. A damaged table is read as far as possible and explained with notes; writing a table always writes a clean and complete one.
  • No EDK2 code. Own UEFI definitions, runtime, platform layer and build tools; the ordinary Linux GCC and ld build the image.

The build

From C sources to a PE32+ EFI application with the ordinary Linux toolchain.

The linker script

tools/efi.lds links at base address 0 with page-aligned .text, .rodata, .data (with the GOT) and .bss, and discards notes, comments and unwind tables. Base 0 makes ELF virtual addresses equal to PE relative virtual addresses, which keeps the conversion trivial. Page alignment gives each PE section its own memory protection (code read+execute, data read+write, never both).

elf2efi.py

  1. keeps .text, .rodata (as .rdata), .data and .bss, checking page alignment;
  2. for every R_X86_64_RELATIVE relocation writes the addend into the section data and records a DIR64 fixup; any other relocation type is a build error (a symbol escaped the hidden visibility);
  3. builds a .reloc section with one block per 4 KiB page;
  4. writes the DOS stub, COFF header (machine 0x8664), optional header (subsystem 10 = EFI application, DllCharacteristics DYNAMIC_BASE | NX_COMPAT) and the section table.

objcopy --target=efi-app-x86_64 produces corrupted relocations with this layout; the converter is short, easy to audit, and fails loudly.

The freestanding runtime

  • Memory: malloc uses AllocatePool with a small header that stores the size (for realloc). Code calls the x wrappers (xmalloc, xstrdup…), which stop the program with rt_fatal on out-of-memory, so callers never check for NULL.
  • printf: fmt.c implements vsnprintf with %d %i %u %x %X %o %c %s %p %%, flags, width, precision and the length modifiers hh h l ll z j t. There is no %f.
  • Strings: libc.c has the usual mem*/str* functions, strto* and qsort; rt.h has inline ctype functions (ASCII only); util.c the string buffer Sbuf and the UTF-8 / UCS-2 conversions.

pal_efi.c

  • Entry point: efi_main sets gST, gBS, gRT, gImage, turns the watchdog off, calibrates the clock, finds the volumes and the arguments, allocates 1 MiB of pages and calls app_main on that private stack (UEFI only guarantees 128 KiB).
  • Console: output converts UTF-8 to UCS-2 and calls ConOut->OutputString; input uses SimpleTextInputEx when available and WaitForEvent with a timer for timeouts (a timeout of 0 polls, which the wipe uses to notice Esc).
  • Volumes: every handle with SimpleFileSystem becomes a volume fsN, sorted by device path text; the one the image was loaded from is the boot volume.
  • Arguments: from the shell parameters protocol when a UEFI shell starts partmgr, else from the load options; partmgr ignores them.
  • Graphics (pal_gfx_efi.c): the Graphics Output Protocol of the console's handle (ConsoleOutHandle), else the first one found.   • Pointer (pal_mouse_efi.c): see The pointer.
  • Serial port: pal_serial_log writes to the serial port only when the ConOut variable sends the console there — an instance of its device path with a UART node — through the Serial I/O protocol found with LocateDevicePath. A machine without a serial console gets nothing.
  • UEFI-only modules (disks_efi.c) include efi_glue.h for the globals and the device path helpers.

Architecture

Layers

Start-up

efi_main (in pal_efi.c) sets up the firmware globals, the volumes and the arguments, switches to the private stack and calls app_main. partmgr switches the console to the narrowest text mode of at least 100 columns and 25 rows, if the firmware has one (pal_con_wide_mode), hides the cursor and loops on the list of disks: every turn calls pm_disks, which locates the block devices again (so R, or any key, rescans), and reads each disk's table to fill the columns. Enter calls pm_disk_screen; Q resets the colours, clears the screen, puts back the text mode partmgr found (only if it changed it) and returns 0 to the caller.

Life of a change

The data model

Three structures carry everything: the disk, the table and its partitions.

PtDev: the disk

typedef struct {
    PtReadFn read;
    PtWriteFn write;   /* NULL: the disk is read-only */
    PtRandomFn random;
    void *ctx;
    uint32_t bsize;   /* bytes per block: 512 or 4096 */
    uint64_t nblocks; /* size of the disk in blocks */
} PtDev;

read and write move whole blocks and return 0 or a PAL_E* code; random fills identifiers. On UEFI ctx is the EFI_BLOCK_IO_PROTOCOL; in pttool it is the image file. write is NULL for the boot disk and write-protected media, and every write function of ptwrite.c then returns PAL_EROFS.

A PtPart has num (the GPT entry index + 1, or 1–4 and 5… on MBR), role (PT_PRIMARY, PT_EXTENDED, PT_LOGICAL), start and size in blocks, the MBR fields mbr_type, active, ebr_lba (the block of the record that describes a logical partition), the GPT fields type_guid, guid, attrs, name (UTF-8), and changed, which puts the star on the screen. pt_free releases the array; a table is otherwise a plain value.

PtFree

pt_free_space returns the free areas as PtFree: start, size and logical, true for an area inside the extended partition, where only a logical partition fits. Areas are aligned and at least 1 MiB; the screen merges them with the partitions and sorts by start.

Reading tables: ptable.c

What block 0 says

pt_read reads block 0 and decides:

  1. 55 AA at bytes 510–511 and every entry's status byte 00 or 80: a valid MBR sector.
  2. An entry of type EE: a protective MBR, so the disk is GPT; other entries next to it make it hybrid.
  3. A valid MBR sector that is not the boot sector of a file system (a jump instruction and NTFS, EXFAT or FAT at their places): an MBR.
  4. Otherwise: if block 1 starts with EFI PART, a GPT whose protective MBR was wiped; if block 0 is a file system's boot sector, a disk formatted without a table; else nothing.

GPT: two copies, checked

gpt_copy reads a header and its entry array and accepts them only if every check passes: signature EFI PART; header size between 92 bytes and one block; header CRC-32 (computed with the CRC field zeroed); MyLBA equal to where it was read; a possible layout (first ≤ last usable < disk size, entry size ≥ 128 and a multiple of 8, at most 1 MiB of array); the array readable and its CRC-32 right. The primary copy is read from block 1, the backup from the primary's AlternateLBA — or from the last block when the primary is damaged. The primary is used when good, else the backup; each failure is a note saying which check failed. Entries whose type GUID is zero are empty and skipped; names are converted from UTF-16.

MBR: the chain of logical partitions

The four entries of block 0 give the primary partitions and at most one extended partition (types 05, 0F, 85). mbr_logicals then follows the chain: each record, at a block inside the extended partition, has in entry 1 its logical partition relative to the record and in entry 2 the next record relative to the start of the extended partition. The walk stops with a note on a record without 55 AA, on a link that does not move forward or leaves the extended partition, and after 128 records — so a looping or broken chain cannot hang partmgr. Logical partitions are numbered from 5 in chain order, as Linux does.

Type names

Two tables at the end of ptable.c, gpt_types and mbr_types, give the names. Their order is the order of the list the user chooses from (pt_type_at); the last four MBR entries (extended and protective) are names only and never offered.

Changing tables: ptedit.c

A table from zero

pt_new replaces the table with an empty one: all fields cleared, lba0 zero (no boot code), new identifiers from dev->random. A GPT gets 128 entries of 128 bytes: the array takes 32 blocks of 512 bytes (4 of 4096), so first_usable is 34 (or 6) and last_usable is the block before the backup array. GUIDs are random with the version 4 and RFC 4122 variant bits set; an MBR signature is random and never zero. PT_NONE is the empty table that pt_write turns into deleting the table.

Free space

Free areas are the gaps between spans. At the top level the spans are the partitions that are not logical, inside the GPT usable area or blocks 1 … min(disk, 232) − 1 of an MBR. Inside the extended partition the spans are:

  • its first block, always reserved: the chain must start there;
  • for each logical partition, the block before it and the partition: every logical partition needs a record somewhere before it, and the block right before it is the one that is always free.

A gap becomes a PtFree after rounding its start up to 1 MiB (for logical gaps, from the block after the gap's first one, which will hold the new record) if at least 1 MiB is left. This rule is what lets the space of a deleted first logical partition be used again: the record of the next one moves to the first block of the extended partition when writing, and the space in front of it is free.

Adding

pt_add checks the request and returns a message for the user, or NULL:

After an MBR change renumber sorts the partitions (primary and extended by number, logical by start) and numbers the logical ones 5, 6…; a partition whose number changes is marked changed.

Delete, type, name, active

  • pt_delete removes a partition; the extended one takes its logical partitions with it.
  • pt_set_type refuses a zero type, and on MBR any change between extended and non-extended types.
  • pt_set_name is GPT only, 36 UTF-16 units.
  • pt_set_active is MBR only, not for the extended partition, and clears the flag everywhere else.

Writing: ptwrite.c

GPT

write_gpt recomputes the last usable block from the real disk size (so an enlarged disk gets its backup at the end) and refuses a table whose partitions do not fit. It builds the entry array (entries at index num − 1, names converted to UTF-16) and writes, in this order:

  1. block 0, the protective MBR — unless the table is hybrid, whose block 0 is left alone: the first 440 bytes as read (boot code; zero for a new table), one entry of type EE from block 1 over the disk (at most 232 − 1 blocks), CHS 00 02 00 as the specification gives, 55 AA;
  2. the primary array at block 2, then the primary header at block 1;
  3. the backup array just before the last block, then the backup header in the last block.

Headers are revision 1.0, 92 bytes, with the array CRC and then the header CRC. Both copies are always written, which is also how a damaged copy is repaired.

MBR

write_mbr writes block 0 with the boot code as read, the signature, one entry per primary or extended partition at slot num − 1, and 55 AA. Before it, a GPT header in block 1 or in the last block is cleared — if it is not inside a partition of the new table — so that no system finds the old GPT. Every entry gets CHS fields computed with 255 heads and 63 sectors, or FE FF FF beyond cylinder 1023.

Then the chain, with the logical partitions in disk order. Record i goes:

  • for the first logical partition, to the first block of the extended partition;
  • for the others, where it was (ebr_lba) if that block is still between the previous partition and this one, else to the block just before the partition — which ptedit.c keeps free.

Entry 1 of a record is its logical partition relative to the record. Entry 2 links to the next record: type 05, start relative to the extended partition, and size from the next record to the end of the next logical partition — the convention of fdisk and sfdisk, which the tests check byte by byte. An extended partition without logical ones gets an empty record with 55 AA.

No table

For PT_NONE, erase writes zeros to block 0, block 1 and the last block: the MBR and both GPT headers, which is what every system looks at. Nothing else is touched.

Backup and restore

The backup file

pt_backup builds the file in memory from the table as read from the disk. All numbers are little-endian.

OffsetSizeContent
08PARTMGR1
84Format version: 1
124Block size of the disk
168Size of the disk in blocks
244Number of extents
28…For each extent: first block (8), number of blocks (4), the blocks
end − 44CRC-32 of everything before it

The extents are block 0 and, for a GPT, block 1, the primary array, the backup header and the backup array; for an MBR, the first block of the extended partition and every logical partition's record. A disk without a table has nothing to back up.

Restore

pt_restore checks the whole file before writing a block: the magic, the CRC, the version, the block size and the disk size (a backup never goes to a different disk), and every extent inside the disk and inside the file, with no data left over. It reads the current table, writes the extents, and — when the backup has no GPT but the disk had one — clears the old GPT's headers and arrays except where a restored partition lies, so that restoring over a changed disk gives back the same blocks (the tests compare the images byte for byte).

Wipe

The engine: pt_wipe

typedef bool (*PtProgressFn)(void *ctx, int pass, uint64_t done, uint64_t total);
int pt_wipe(const PtDev *dev, uint64_t start, uint64_t count, PtProgressFn progress, void *ctx);

pt_wipe overwrites count blocks from start in two passes — random data, then zeros — in chunks of 4 MiB (the last one shorter). The random data comes from xoshiro256**, seeded with 32 bytes from dev->random: the aim is to overwrite every byte with data that has no relation to the old contents, not to be unpredictable, and a fast generator keeps the pass at disk speed. The buffer is filled again for every chunk, so no two chunks are alike.

The progress function is called before the first chunk of each pass (done = 0) and after every chunk, with the pass and the blocks done in it. When it returns false the wipe stops and returns PAL_EABORT; a failed write stops it with that write's error. A disk without a write function gets PAL_EROFS, a range outside the disk PAL_EINVAL.

The rules: pt_can_wipe

pt_can_wipe (in ptedit.c) refuses the extended partition of an MBR — its blocks hold the logical partitions and the chain of their records — and every partition while the table has unwritten changes, when the position on the screen may not be the one on the disk. A logical partition is wiped from its first block to its last: its record lies before it and is not touched.

Progress on the screen

wipe_partition in diskview.c checks may_change and pt_can_wipe, shows the red warning (with the note about flash drives instead of the backup hint) and calls pt_wipe with wipe_progress. That function polls the keyboard without waiting; Esc asks with ui_yesno and a yes returns false. It redraws the box at the start and end of each pass and at most five times a second in between (draw_wipe): pass, a bar of █ and ░, the percentage of the pass, the amount written in it, the speed over both passes so far and the time left for both (fmt_time), estimated after half a second. Nothing else is drawn during the wipe, so the console keeps up with the disk.

The UEFI program

Finding the disks: disks_efi.c

pm_disks locates every handle with EFI_BLOCK_IO_PROTOCOL, sorts them by device path text and names them blkN by position — so a disk keeps its name from one start to the next — then keeps the whole disks with a medium and a block size of at least 512. The disk partmgr was loaded from is the one whose device path the path of gLoadedImage->DeviceHandle (the partition) starts with, followed by /; it and write-protected media get write = NULL. The kind (NVMe, SATA, USB…) comes from the node names in the device path.

Block I/O goes through a page-aligned bounce buffer from AllocatePages, which satisfies any IoAlign; every write is followed by FlushBlocks. Random bytes come from EFI_RNG_PROTOCOL when the firmware has it, else from a SplitMix64 generator stirred with the time-stamp counter and the clock.

Drawing and dialogs: ui.c

ui_text writes a UTF-8 text at a position, padded or cut to a width counted in characters; it never writes the last cell of the screen, which scrolls some consoles. Dialogs are boxes in the middle of the screen, drawn over it: the caller redraws the screen before the next dialog (draw in diskview.c). ui_keybars draws the one or two key bars at the bottom: a group name, then each key white on blue with its action after it, always the same keys in the same colours, so the bars never move (a key that does not apply answers with a message instead). Both bars use one style, the widest that fits: boxes with a space on each side and the group names, then narrow boxes, then narrow boxes without the names. ui_input shows a field whose proposed text is replaced by the first character typed; ui_menu is a scrolling list; ui_yesno takes Y, N, Esc. With warn set they are white on red: every operation that destroys data uses them.

The screen of a disk: diskview.c

A View (view.h, shared with the window) holds the disk, its PtTable, the rows (partitions and free areas merged by start), the selection and the message line; view.c reads the table (pm_view_load), builds the rows (pm_view_rows), writes the message line (pm_say) and the type names (pm_type_text). Every action follows the same pattern: may_change refuses on the boot disk and read-only media; dialogs collect the input; one pt_* call changes the table and returns a message on refusal; pm_view_rows and pm_say update the screen. Only three functions reach the disk: write_table (Write), restore, wipe_partition and backup (which only reads it); the first three go through confirm_destroy, the red warning answered with Y or N (ui_yesno, where Enter does nothing, so a key pressed twice cannot write); a refusal leaves Nothing was written. on the message line. After writing, the table is read back from the disk, so the screen shows what the disk holds.

Sizes: units.c

pm_parse_size reads a number with up to six decimals (point or comma) and a binary unit (B, K, M, G, T, optionally followed by B or iB; s for blocks; no unit means MiB), or rest/all/max, and refuses overflows. pm_fmt_size prints one decimal (194.9 MiB); pm_fmt_exact prints whole MiB or GiB when exact, so that a proposed start reads back to the same block.

The graphical interface

Being built (decisions P18–P25): the drawing, the font, the pointer, the window, its actions and every screen size are done; the user manual comes next. Without a graphics screen partmgr.efi shows the text screens of 0.1.2.

Drawing: gfx.c

A GfxCanvas is an image in memory, w × h pixels of 0x00RRGGBB, with a clip rectangle outside which nothing is drawn. The code is portable and uses integers only (the UEFI build has no floating point), so the same canvases are drawn on Linux by the tests.

FunctionDraws
gfx_fill, gfx_frameA rectangle; a frame of some pixels inside one.
gfx_round_rectA rectangle with rounded corners and an optional border. Each corner pixel is blended by how much of it the shape covers, counted on 4 × 4 samples in eighths of a pixel.
gfx_hatchDiagonal lines every few pixels: the free space in the disk bar.
gfx_text, gfx_text_widthUTF-8 text in a line whose top is given; its width.
gfx_clip, gfx_unclipLimit drawing to a rectangle, for example a label to its block.
gfx_arrowThe mouse pointer: an arrow of 12 × 19 pixels, white with a black outline, at a whole multiple of that size.

The font

partmgr has no font engine. tools/gen-font.py renders Inter once with Pillow — sizes 16, 20, 26, 32, 40 and 52 pixels, regular and semibold, ASCII, Latin-1 and a few punctuation marks and arrows — into grey levels of 4 bits per pixel, and records for each glyph its advance in 1/64 pixel (unrounded, as Raqm lays text out), its offset from the baseline and its size, and for each face the kerning of the ASCII pairs that differ by at least an eighth of a pixel. gfx_text places each glyph at the rounded position, adds the kerning of the pair, and blends the grey levels between the background and the colour. Characters Inter lacks are drawn as ?. gfx_font picks the largest size not above the one asked for. The file is about 700 KB; its layout is described at the top of gen-font.py, and gfx_fonts_init checks every offset before the first use.

The pointer

OVMF has no mouse driver at all, and a real firmware may lack one too, so partmgr brings its own for USB mice (decision P21). pal_pointer_open gathers two kinds of devices:

  • The firmware's pointers: every Simple Pointer and Absolute Pointer protocol on a handle with a device path — a real device. The console's own pointer has none: it only adds up the others, and exists even when there is no mouse, so it is left out. Relative counts become pixels at about one pixel per count at 8 counts per millimetre; absolute positions are scaled to 0…65535.
  • partmgr's USB mice: every USB I/O interface of class HID, subclass boot, protocol mouse (3, 1, 2) with an interrupt-in endpoint. partmgr opens it BY_DRIVER, as a driver does: when a firmware driver already has it the open is refused and the mouse is the firmware's. Otherwise partmgr sends SET_PROTOCOL (boot) and SET_IDLE, and starts an asynchronous interrupt transfer: the host controller polls the mouse at the endpoint's interval and calls report with each report — buttons, x, y — which adds the movement up. pal_pointer_read takes the sums at TPL_NOTIFY, so a report cannot arrive halfway. When no USB interface exists at all, the USB host controllers are connected first: a firmware that starts fast may not have looked at the devices.

pal_pointer_close stops the transfers and closes the interfaces, so the firmware gets the mice back. Tablets and touchscreens have no boot protocol; they work only through a firmware driver. The pointer is drawn only when a device was found. Two cases cannot be tried in QEMU: a firmware that has a mouse driver, and one that has not connected its USB controllers.

The window: gui.c

app_main calls pm_gui first, before any change of the text mode (which on some firmware changes the screen too); it returns false, with nothing changed, when pal_gfx_open finds no graphics screen, and the text screens run. The window follows the approved mockup (docs/assets/gui-mockup.png):

  • Layout (layout): the font by the screen's height — 16 pixels up to 600 rows, 20 up to 900, 26 up to 1300, 32 up to 1700, 40 up to 2000, 52 above, so that 1080 and 2160 rows have the same proportions — and every measure from its line height: the title bar, the list of disks (a quarter of the width, within 10 and 14 lines; 8 below 800 pixels), the disk's line, the bar (two lines high), the table (as many rows as fit above the notes), the message line and the rows of buttons. The buttons keep the group names Partition: and Disk: when both rows fit, else lose them, else get narrower margins and gaps, else go on as many rows as they need. The columns of the table keep the proportions of the mockup but are never narrower than a number, a size or a type. In a narrow list the kind of disk moves to the second line, and a note that does not fit is split after its colon.
  • Very large screens are drawn at their own resolution, with the faces of 40 and 52 pixels: the text stays sharp. Above 1700 rows the pointer is drawn twice as large.
  • The disks: name, kind and size, the table and the number of partitions (read once, and again with F5), and started from here: read only or write-protected. At start the first disk partmgr may change is opened.
  • The bar: every row at its place to scale (at least 3 pixels wide), coloured by type — EFI orange, Linux green, swap red, Microsoft and FAT blue, others lilac —, the free space hatched, the extended partition a band around its logical partitions. A label is whole, or the number only, or absent: never cut. The selected row is framed.
  • The table: the columns of the text screen at the proportions of the mockup; a cell may run over the next ones while they are empty; changed partitions in amber with their *, free space in grey.
  • Keys: the arrows, Home and End move in the list that has the keys — the rows, or the disks after Tab, which moves them back and forth; its selection is blue, the other's pale. Page Up and Page Down change the disk at any time, F5 reads the disks again, Esc quits.
  • The mouse: a click on a button is its key; on a disk it opens it; on a row of the table or a block of the bar it selects it. The button under the pointer is highlighted. The pointer is drawn on the screen over the canvas, which stays as it is, so moving it copies only the two small areas it leaves and enters.

Actions and dialogs

The window does not have actions of its own: every action key — and every click on an action button, which is that key — goes to pm_disk_action in diskview.c, the same function the text screen calls, with every question, check and message of 0.1.2. Two hooks make it draw on the window:

  • ui_dialogs (ui.h): while the window runs, ui_message, ui_yesno, ui_input and ui_menu are its dialogs — a box in the middle of the dimmed window, blue title or red for a warning, the text wrapped to its width, buttons with their keys. They take the same keys as in text (the Y/N question takes Y, N, Esc, and Enter does nothing, so a key pressed twice cannot write), and the mouse: a click on a button, on an item of a list (which chooses it). A field shows the proposed text selected, replaced by the first character typed, and a caret.
  • pm_screen (view.h): redraw draws the window where the text screen draws itself before a dialog; wipe draws the progress of a wipe in a red box — pass, bar, percentage, amount, speed and time left — with a Stop button; wipe_stop reports Esc or a click on it, and the question Stop the wipe? follows as in text.

Leaving a disk with unwritten changes — another disk, F5, Esc — asks Discard the unwritten changes? (Y/N) first, as leaving the screen of a disk does in text. After an action the summary of the disk in the list is read again.

After every drawing log_window describes the window on the serial port of the console (pal_serial_log), one line per item, each with the point to click on: gui: disk …, gui: shows …, gui: row … (the cells as the text screen writes them, < on the selection, the place in the table and in the bar), gui: button … (hover under the pointer), gui: buttons … (their rows and right edge), gui: focus …, gui: message …, gui: pointer …, then gui: shown; gui: window W×H font F opens it. Dialogs add gui: dialog TITLE: TEXT (the whole text, not wrapped), gui: dbutton …, gui: field … after every change, gui: item … for the visible items of a list, gui: dialog shown and gui: dialog closed; a wipe adds a gui: wipe … line at every update, with the place of Stop. The QEMU test reads the window from there. On a machine whose console is not on a serial port nothing is written.

Testing

The table code is tested on Linux against sfdisk and parted; the program is tested in QEMU.

pttool

tests/partmgr/pttool.c is the table code compiled for Linux (with AddressSanitizer and UBSan) around an image file. It reads the table, runs commands on it in order, and prints the result as key=value lines:

$ build/tests/pttool disk.img new gpt add primary 2048 204800 C12A7328-F81F-11D2-BA4B-00A0C93EC93B "EFI" write
$ build/tests/pttool disk.img del 2 free
$ build/tests/pttool disk.img backup table.bin
$ build/tests/pttool disk.img -b 4096 size 1.5G

Commands: new gpt|mbr|none, add primary|logical START SIZE TYPE NAME, del, type, name, active, free, write, reread, backup, restore, size, and wipe N [PASS CALL], which wipes partition N and, with PASS and CALL, stops when the progress function is called for the CALL-th time in pass PASS — as if Esc had been pressed. An error prints error=MESSAGE and exits with 1.

The table tests

tests/partmgr/run-tests.py, run by make test:

  • Reading. Images built with sfdisk — GPT with 512- and 4096-byte blocks, gaps, entries out of order, accented names, attributes; MBR with primary, extended and logical partitions; empty tables — must read exactly as sfdisk --json reports them. Then 13 kinds of damage (broken primary header or array, broken backup, both broken, wiped protective MBR, hybrid MBR, enlarged disk, looping chain, record without signature, partition beyond the end, whole-disk FAT, invalid entries) must be read as well as possible and noted.
  • Sizes. What pm_parse_size accepts, refuses and prints.
  • Writing. Every table partmgr writes is read back by sfdisk (which must find what was asked and nothing wrong with --verify) and by parted: new tables, logical partitions creating the extended one, changes to tables made by sfdisk (identifiers of untouched partitions unchanged), deleting and refilling the first logical partition, deleting the extended one, GPT to MBR and back, deleting a table, repairing, an enlarged disk, boot code kept or cleared, a hybrid MBR left alone, and the refusals.
  • Independently of partmgr, a Python function reads every MBR written byte by byte (CHS fields, the chain, the link sizes) — and agrees with the MBRs sfdisk writes.
  • Backups are restored over a changed disk, which must equal the original byte for byte; backups of another disk, damaged ones, and disks without a table are refused.
  • Wipe. Partitions hold known patterns; a wipe must leave its partition all zeros (also when its size is not a whole number of chunks, and with 4096-byte blocks), the neighbours, the table and — for a logical partition — the chain untouched, and call the progress function once per chunk in order. Stopped when pass 2 starts, the partition must hold random data everywhere (every block different, all byte values); stopped after the first chunk, only that chunk may have changed. The extended partition and a table with changes are refused.

The tests were checked by breaking the code on purpose — logical numbering, sizes off by one, the boot flag, the backup GPT's CRC, the link sizes of the chain, the CHS heads, a wipe with one pass only or written one block off: each break fails them. Where sfdisk lacks --sector-size (util-linux 2.39, the version of Ubuntu 24.04 and of CI) the 4096-byte comparisons are skipped and the script says SKIPPED.

The drawing

build/tests/gfxtool check, run by make test with AddressSanitizer and UBSan, checks the drawing on its own: the faces chosen for each size, kerning (AV narrower than A plus V), missing characters, text with opaque and smoothed pixels that stays in its line and returns its end, clipping, fills cut to the canvas, rounded rectangles (symmetric, bordered, smoothed corners, nothing outside), the hatching and frames, the pointer's arrow (at one and two times its size, cut by the edge), and the test picture at three sizes. gfxtool scene W H FILE [X Y] writes the test picture of tests/partmgr/gfxscene.c — every primitive and every face, laid out like the window — as a PPM file, with the pointer at X, Y when given; the QEMU test compares it with the screen.

In QEMU

make qemu-test runs tests/partmgr/qemu-test.py. It boots QEMU/OVMF from a virtual FAT disk holding partmgr.efi as \EFI\BOOT\BOOTX64.EFI, so the firmware starts it, attaches test disks made by sfdisk, and drives partmgr with sendkey through the QEMU monitor. Everything partmgr draws also reaches the serial console; the test strips the terminal sequences, makes every run of blanks one space (so dialog texts wrapped over two lines still match), and waits for the expected text after the previous match — the screen is drawn top to bottom, so rows come before the message line under them. The first two parts run QEMU without a video card (-vga none): with no graphics screen partmgr shows its text screens, which they check. The boot disk is then blk0 or blk1, as the PCI slots fall.

  1. Looking: the list (the boot disk marked), every row of both disks, the return to the firmware (its setup menu starts), and the disks identical byte for byte.
  2. Changing: the boot disk refuses; on the GPT disk a new partition (start, size, type, name), a rename, a delete, Esc asking, Write answered first with Enter and N (nothing written), then with Y; a wipe of the new partition, with both passes and the amount on the console, and a wipe of a bigger one stopped with Esc (the GPT disk's writes are slowed to 60 MB/s with QEMU's throttling.bps-write, so that there is time to press it); on the MBR disk a logical partition (renumbering the next one), the active flag, a backup to a writable FAT disk, Write, delete the table, restore. Then, outside QEMU, sfdisk must find the GPT disk exactly as asked and the MBR disk exactly as before, and the data must be right: the wiped partition all zeros, the stopped one changed at its start and not at its end, the others untouched.
  3. Drawing: gfxdemo.efi draws the test picture on the graphics screen, once at the firmware's resolution (1280 × 800 in OVMF) and once at 1024 × 768 (QEMU's VGA with xres and yres), and says so on the serial port through pal_serial_log. QEMU's screendump must be, pixel for pixel, the picture gfxtool draws on Linux at the same size. Broken on purpose — the copy to the screen one row short — the check fails with exactly one row of pixels different.
  4. Pointing: gfxdemo.efi with QEMU's USB mouse on an xHCI controller must report firmware 0, partmgr's USB driver 1. The mouse is moved with the monitor's mouse_move in eleven steps of (−40, −25) from the middle of the screen; mouse_button must give a click and a release at exactly that point, and the screen must be the test picture with the arrow there, pixel for pixel. Moved far past the top left corner, the pointer must stop at 0,0. A USB tablet (no boot protocol) and no USB device at all must find no pointer. Broken on purpose — the vertical movement reversed — four checks fail.
  5. The window: partmgr with the video card and QEMU's USB mouse, on fresh copies of the two test disks. From the description on the serial port: the three disks (the boot disk read only, the GPT disk opened), every row, the buttons; on the screen, the title bar and the selected row in their colours. Keys: a row down, Tab to the disks and back, a disk down and up (the MBR disk with its logical partitions and free areas), Page Down, Page Up, F5, an action key. The mouse, moved to the points the description gives: a click on a disk, on a row, on a block of the bar, on a button; the button under the pointer highlighted; Quit, and the firmware goes on. The disks must be unchanged, byte for byte.
  6. Changing in the window: the journey of part 2 again, on fresh disks and a writable FAT disk, with the mouse and the keys and the window's dialogs: the boot disk refuses (the message closed with OK); on the GPT disk a new partition from the N button (start, size, a type from the list, a name), a rename, a delete with the D button; quitting and changing the disk with changes ask, and No stays; Write from its button asks, Enter does nothing, N cancels, a click on Yes writes; a wipe, and a second one stopped with a click on Stop; on the MBR disk a logical partition whose type is clicked in the list, the active flag, a backup from its button, Write, delete the table, restore. Afterwards the same checks as part 2, by verify_changes. Broken on purpose — Enter answering Yes — the check Enter does nothing fails, and with it the rest of the journey and the checks of the data: 31 in all.
  7. Sizes: the window at 640 × 480, 1024 × 768, 1920 × 1080 and 3200 × 1800 (QEMU's VGA with xres, yres and enough video memory): the font chosen by the height (16, 20, 26 and 40 pixels), the buttons inside the screen, the title bar's colour on the screen, a click on a disk. OVMF does not offer 3840 × 2160: the face of 52 pixels is not tried on a screen.

Extending partmgr

Adding a partition type

Add the GUID and name to gpt_types, or the byte and name to mbr_types before the last four entries, in src/partmgr/ptable.c. The order is the order of the list on the screen. Add the type to the tables of the user manual, and a check in run-tests.py if its name matters.

Adding an action to the screen of a disk

  1. Put the change of the table in ptedit.c, as a function that returns NULL or a message and sets changed; test it through a new pttool command.
  2. In diskview.c, write the action: may_change, the dialogs (redraw with draw before each), the call, build_rows, say. Add its key to the loop of pm_disk_screen and to the key bar in draw.
  3. Anything that writes a disk must go through confirm_destroy.
  4. Extend qemu-test.py, and describe the key in the user manual.

Adding a note

Call note(t, ...) in ptable.c where the problem is found, add the damaged case to run-tests.py with has_note, and explain it in the table of notes of the user manual.

Conventions

  • C11 with GNU extensions, 4-space indentation, braces on the same line, snake_case; file-local functions and data are static. Comments explain why, in English, and are short; every file starts with a comment saying what it contains.
  • Text is UTF-8; conversion to and from UCS-2 happens only at the firmware boundary.
  • No code, headers or libraries from EDK2: protocol and structure definitions are written from the UEFI specification.
  • Keep the build free of warnings and the tests green; add a test with every fix.
  • Delete a partition: remove it from the table. Wipe: destroy its contents. The code, the texts and the manuals never use one for the other.
  • Blocks are written only in ptwrite.c, and only by pt_write, pt_restore and pt_wipe.
  • Messages for the user are sentences without a capital or a full stop at the end when they come from the table code (pt_add and friends); the screen puts them in dialogs as they are.
  • Line counts in this manual are generated: run make docs after changing a file.

Glossary

Block I/O
The UEFI protocol that reads and writes the blocks of a disk or partition.
CHS
Cylinder/head/sector addresses of old BIOSes, still stored in MBR entries next to the block numbers.
EBR
Extended boot record: the one-block table in front of each logical partition, chained to the next.
Extent
A run of blocks saved in a backup file, with its position.
Hybrid MBR
A GPT disk whose block 0 also lists some partitions for BIOS systems; partmgr reads it as GPT and leaves block 0 alone.
Note
A sentence the reader adds to a table about something unusual it found.
Protective MBR
Block 0 of a GPT disk: one entry of type EE over the disk.
Span
In ptedit.c, a run of blocks in use; free areas are the gaps between spans.
